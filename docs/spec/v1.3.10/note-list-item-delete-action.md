# ノート削除導線の一覧側移設仕様書

## ドキュメント情報
- バージョン: 1.3.10
- 更新日: 2026-05-22
- ステータス: 設計書
- 分類: UI改善
- 関連Issue: #90 削除ボタンの位置を一覧側に持っていったほうが良い

---

## 1. 概要

### 1.1 背景・課題
現在の削除操作は contents footer に配置されているが、同じ footer には表示モード切替ボタンが並んでおり、設定操作と破壊的操作が同一グループに混在している。

Issue #90 の要望では、Gmail のようにノート一覧アイテム側へ削除アイコンを配置し、既存の footer 側 delete note を撤去することが求められている。

### 1.2 目的
- 削除操作を対象ノートの近傍へ移し、文脈に沿った操作導線にする。
- 表示モード切替と削除操作を分離し、誤操作リスクを下げる。
- 将来、一覧アイテムへ複数アクションを追加できる拡張可能な構造にする。

### 1.3 スコープ
- ノート一覧アイテムにアクション領域を追加する。
- 削除アクションを一覧側から実行可能にする。
- contents footer の delete note ボタンを削除する。
- 既存の削除確認ダイアログと deleteProject 実行ロジックは継続利用する。

---

## 2. ユースケース

### 2.1 一覧から削除する
1. ユーザーがノート一覧を表示する。
2. 任意のノート項目にフォーカスまたはホバーする。
3. ノート項目内の削除アイコンを押す。
4. 確認ダイアログを表示する。
5. OK でノートを削除し、キャンセルで何もしない。

### 2.2 将来アクションを追加する
1. 開発者がノート一覧アイテムのアクション領域へ新規ボタンを追加する。
2. 既存の削除ボタンと同一レイアウト規約で表示できる。
3. クリックイベントがテキスト選択イベントと衝突しない。

---

## 3. 機能要件

### 3.1 UI配置要件
- ノート一覧の各 noteListItem 内に action コンテナを追加する。
- action コンテナ内に削除アイコンボタンを配置する。
- contents footer から delete note ボタンを削除する。

### 3.2 操作要件
- 削除アイコン押下時、対象ノートをアクティブ化してから削除確認へ進む。
- 確認ダイアログの文言と挙動は既存仕様を踏襲する。
- 削除確認 OK 時に deleteProject を実行する。
- キャンセル時は状態変更を行わない。

### 3.3 イベント分離要件
- ノート本文領域クリックは既存どおり選択操作とする。
- アクションボタン押下は選択領域クリックと独立して動作する。
- アクション押下時に不要な二重イベント伝播を発生させない。

### 3.4 アクセシビリティ要件
- 削除ボタンは button 要素を使用する。
- aria-label と title に delete note を設定する。
- キーボードフォーカスで操作可能であること。

### 3.5 拡張性要件
- 一覧アイテム内に noteListItem-actions（仮称）領域を定義し、複数ボタン追加を前提にした DOM 構造にする。
- 1アクション1ボタンの責務分離を維持する。
- 将来のピン留め、複製、共有などの追加時に既存削除ボタンの修正を最小化する。

---

## 4. 非機能要件

### 4.1 パフォーマンス
- 一覧描画に対する追加コストは軽微であること。
- 大量ノート時でもスクロール性能を著しく劣化させないこと。

### 4.2 互換性
- 既存の deleteProject ミューテーション仕様を変更しない。
- 既存の表示モード切替機能（F8/F9/F10）へ影響を与えない。

### 4.3 保守性
- 削除ロジックをコンポーネント間で重複実装しない。
- 既存の DialogHelper 経由の削除確認フローを再利用する。

---

## 5. インターフェース定義

### 5.1 コンポーネント責務
- NoteList
  - 一覧アイテム内の削除アクション UI を提供する。
  - 対象ノート URI を親へ通知する。
- MainContents
  - NoteList から受け取った削除要求を受理する。
  - 必要に応じて対象ノートをロードし、削除実行を委譲する。
- Contents
  - footer 上の削除ボタンを持たない。
  - 既存の表示モード切替とタイトル編集責務に集中する。

### 5.2 イベント契約
- NoteList から親へのイベント（例）
  - onDelete(uri: string): 対象ノートの削除要求
- 親での処理順序（例）
  1. loadProject(uri)
  2. 削除確認ダイアログ表示
  3. OK 時 deleteProject

注記:
- 既存実装に合わせ、イベント名や実装方式は最終実装時に確定する。
- 本仕様の必須条件は、対象ノートを誤らず削除できるイベント契約が成立すること。

## 9. テストケース要約

### 9.1 Unit
- NoteList
  - 各アイテムに削除ボタンが描画される。
  - 削除ボタン押下で onDelete に対象 URI が渡る。
  - 削除ボタン押下時に onSelect と競合しない。
- MainContents
  - NoteList の onDelete ハンドラが削除フローを開始する。
  - 削除対象が非アクティブ時でも正しいノートが削除される。
- Contents
  - delete note ボタンが描画されない。
- DialogContents
  - 削除確認 OK で deleteProject が呼ばれる。
  - キャンセル時に deleteProject が呼ばれない。

### 9.2 回帰
- 表示モード切替ボタン（F8/F9/F10）の表示・操作。
- タイトル編集、ノート選択、検索入力の既存挙動。
